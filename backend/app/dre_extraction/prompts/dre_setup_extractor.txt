STEP 2: Determine assessment setup type
Identify the structural pattern this HOA follows. Pick the value
whose definition matches what THIS document actually shows. Do not
pick "unknown_needs_review" unless you have read every relevant page
and still cannot decide.

Allowed setup_type values and what each one means:
- fixed_equal: every unit pays the identical dollar amount.
- grouped_category: units are bucketed into named groups (by
  floorplan, building, size, or similar) with one assessment amount
  per group; amounts may differ across groups.
- individual_unit: each unit has its own row with a custom dollar
  amount and there is no grouping.
- multi_pool_combination: per-unit amounts are produced by adding
  contributions from multiple cost pools (general common +
  residential + parking + commercial + fire + water/sewer + cost
  sharing + limited-use + other components, in any combination).
- unknown_needs_review: relevant pages are present but the setup
  cannot be confidently classified. Use ONLY as a last resort.

STEP 5: Extract allocation pools
Identify every cost pool the DRE uses to allocate assessments.

Before listing per-pool fields, apply these completeness rules so
you don't undercount pools (the most common extraction defect on
multi-pool DREs):

5a. Pool-count anchor.
If any inventory page is classified as "per-unit assessment
schedule" and has multiple dollar-amount columns, count the dollar
columns (excluding any "Total" or "Unit" identifier column). That
count is the EXPECTED NUMBER OF ASSESSMENT-RELATED COMPONENTS —
not a hard quota of allocation_pools. For each non-total dollar
column, produce EITHER an allocation_pool entry OR a
human_review_question explaining why the column is NOT a regular
allocation pool (e.g. pass-through, reimbursement, special
assessment, reserve-only, or informational-only column).
This prevents:
- silently producing fewer pools than the schedule shows, AND
- fabricating a pool for a column the DRE treats as separate from
  regular assessment.

5b. Budget-section sweep.
Before finalizing the pools list, walk every inventory page whose
page_type is one of:
  annual operating budget
  supplemental budget
  commercial common budget
  limited common budget
  master association budget
  parking schedule
  residential/common/commercial pool schedule
  cost sharing fee schedule
Each titled budget section with its own subtotal/total row = one
allocation_pool. Do NOT combine sections the DRE keeps separate.

5c. Pool-family checklist.
Common pool families to check for. This is a CHECKLIST for
completeness — NOT a quota, and NOT an assumption that any of
these families exist in THIS DRE:
- General Common / Master
- Residential Common
- Commercial Common
- Parking / Garage
- Limited Common (per-building or per-cluster)
- Cost-sharing / Master Association
After your sweep, ask per family: "is the DRE silent on this
family (correct: omit), or did I miss it (extract it now)?" Never
extract a family the DRE doesn't show.

5d. Component sub-pool extraction.
When a parent budget section has INTERNAL subdivisions where
DIFFERENT allocation math applies to different portions of the
same section — for example a section with both a prorated half
(allocated by some per-unit factor) AND an equal half (allocated
equally across recipient units) — produce ONE allocation_pool
entry PER component, NOT one pool for the parent section.

Signals that a budget section has component sub-pools:
- The per-unit assessment schedule has TWO OR MORE columns
  referencing the same parent name but with different math labels
  (e.g. one column ending in "Prorated" and another in "Equal",
  both prefixed by the same parent-section name).
- A "proportionate budget components" page explicitly explains
  the split (the DRE often lists, line-by-line, which budget
  items are prorated vs equal).
- The DRE shows separate annual totals for the prorated and
  equal portions within one parent section.

Component-pool naming convention (universal, not DRE-specific):
- pool_key = `{parent_key}_{component_method}` where
  component_method matches the allocation_method enum value
  you assigned (e.g. `<parent>_prorated` with
  allocation_method=ownership_percentage or
  allocation_method=square_footage; `<parent>_equal` with
  allocation_method=equal).
- Set `parent_pool_key` on EACH component pool to the shared
  snake_case parent identifier (derived from the parent budget-
  section name). This lets downstream code group components back
  into their parent section without string-parsing.

When you DON'T see these signals, do NOT fabricate components.
Single-component pools (most fixed_equal and ownership-only
setups) remain one allocation_pool entry with `parent_pool_key`
unset.

Per-component budget-line attribution. When you emit two or more
component sub-pools sharing the same `parent_pool_key`, each
component's `included_budget_lines` MUST reflect the
per-component split documented in this DRE — typically on a page
classified as `proportionate budget components` or equivalent.
Specifically:
- if the DRE specifies which budget items go to the prorated
  component and which go to the equal component (line by line
  or by category), emit those lines on the matching component
  only;
- if the DRE shows separate annual totals per component but does
  NOT specify the line-level split, leave `included_budget_lines`
  empty on each component AND emit one human_review_question
  (severity=medium) asking the operator to define which budget
  lines go to which component.

Do NOT copy the parent budget section's full line list to every
child component. Duplicating the line set across children causes
double-counting in downstream budget mapping.

For each pool, derive:
- pool_key: a stable snake_case identifier based on the pool's
  purpose. Examples: equal_costs, variable_costs, general_common,
  residential_common, parking_garage, fire_cost_sharing. Use the
  same key for the same conceptual pool across re-extractions.
- pool_name: human-readable display name.
- annual_amount / monthly_amount: the DRE-stated totals (preserve
  verbatim). If only one is printed, leave the other null — never
  divide or multiply by 12 silently.
- allocation_method: pick the value whose definition matches the
  DRE's actual allocation rule.
    * equal: pool is divided equally among recipient units.
    * square_footage: share is proportional to unit sqft / total
      sqft.
    * ownership_percentage: share is the DRE-stated ownership %
      (undivided interest).
    * category: share depends on the unit's category / group.
    * specified_value: each unit has its own per-unit dollar
      amount explicitly listed in the DRE (no formula).
    * parking_space: allocated only to parking-space holders.
    * custom_factor: DRE uses a custom factor or denominator
      that doesn't match any of the above methods.
    * unknown: method is visible but unclear and needs review.
- recipient_scope: who pays this pool. Free-text values like
  all_units, residential_units, commercial_units, parking_units,
  specific_groups, or custom are all acceptable.
- denominator_value + denominator_label: the divisor used to split
  the pool. Use the DRE-stated value verbatim.

  DENOMINATOR-SCOPE CONSISTENCY: denominator_value MUST match the
  unit count implied by recipient_scope. When recipient_scope
  excludes some units (e.g. residential-only, commercial-only,
  parking-only), the denominator counts ONLY the included units,
  NOT total_units. If the DRE-stated denominator disagrees with
  the scope-implied count, preserve the DRE value verbatim (DRE
  is the law) and record a validation_check with status=fail
  describing the disagreement.

- denominator_source: whether the denominator is printed verbatim
  in the DRE, computed from other rows, or unclear. The field
  description has the semantic definition.
- included_budget_lines / excluded_budget_lines: the budget-line
  labels (verbatim) that this pool funds.

  PASS-THROUGH DETECTION: within each budget section, flag any
  line item whose label contains pass-through signal words —
  "reimbursement", "pass-through", "individually billed",
  "sub-metered", "third-party billed", "surcharge", "special
  assessment", "capital contribution". For each such line:
  * Keep the label verbatim in included_budget_lines (preserves
    audit trail).
  * Produce one human_review_question with severity=medium asking
    the operator to confirm whether the per-unit amount should be
    included in the regular assessment or excluded as a
    pass-through. Quote the per-unit AND annual amounts in the
    question text.
  * Do NOT double-count: if the DRE's "Total Income" / "Total
    Operating" / "Total Operating and Reserves" row already
    includes the pass-through line, preserve that total verbatim
    and let the operator decide via the review question.

  SPECIAL EXCEPTION — printed per-unit special-line columns.
  When the per-unit assessment schedule prints a DOLLAR COLUMN
  for a special-line item (unfunded-liability allocation,
  capital-contribution allocation, one-time-assessment
  allocation, special-assessment allocation, etc.), the column
  is still "accounted for" under STEP 5a in one of two ways:
  - If the DRE specifies an allocation rule (equal across all
    recipient units, by ownership %, etc.) produce an
    allocation_pool entry for it with allocation_method set to
    that rule. Set parent_pool_key to the parent budget section
    if there is one; otherwise leave it unset.
  - If the column shows raw per-unit dollar amounts with no
    stated allocation rule, use allocation_method=specified_value
    and capture the per-unit amounts as factor_type=dollar_amount
    entries in each unit's pool_factors (keyed by this pool's
    pool_key).
  In both cases, also produce one human_review_question with
  severity=medium asking the operator to confirm whether the
  column should be included in regular assessment or treated as
  a separate one-time / disclosure-only item.

- source_pages: at least one page where this pool is documented.

STEP 8: Validate calculations
Run these math checks against the values you extracted:
- Do group totals sum to total units?
- Do unit ownership percentages sum to 100%?
- Does total square footage match the DRE denominator?
- Does variable_factor × unit_size match the variable assessment?
- Does base + variable equal the total assessment?
- Do group totals × unit counts equal the total monthly budget?
- Are values rounded to cents consistently?
- Are there visible rounding differences worth flagging?
- Are there missing columns or unclear values?

When multiple pools exist, ALSO run these per-pool checks:
- annual_amount / denominator_value / 12 ≈ printed monthly
  per-unit amount for this pool (within $0.50 rounding).
- If a per-unit assessment-schedule page exists, sum that pool's
  per-unit column and × 12 — does it equal annual_amount?
- Sum of pool annual_amount ≈ total annual budget (when both are
  printed).
- Sum of per-pool reserve contributions ≈ total reserve
  contribution (when both are printed).
- Each pool's recipient_scope count matches its denominator_value.

Run this check REGARDLESS of whether a per-unit assessment
schedule exists:

  budget_section_pool_coverage: For every titled budget section
  in the inventory (every page that prints a "Total Income" /
  "Total Operating and Reserves" / "Total Budget" / "Annual
  Total" row), record one of two outcomes:
  - status=pass: a matching allocation_pool entry exists for this
    section.
  - status=fail: the section is explicitly marked non-assessment
    / informational / pass-through / excluded, AND a
    human_review_question was produced for it.

  This catches missed pools even when no per-unit assessment
  schedule is present (e.g. single-page schedules, scanned
  appendices).

Component-pool requirement. When ANY allocation_pool has
`parent_pool_key` set (a component sub-pool), you MUST emit ONE
validation_check per component pool, named `<pool_key>_math`.
The check verifies the component's annual_amount against the sum
of per-unit contributions for that component:

- For an `equal` component: (annual_amount / denominator_value
  / 12) ≈ printed monthly per-unit amount for this component
  (±$0.50 rounding).
- For an `ownership_percentage` / `square_footage` / `category`
  component (any prorated component): Σ(per-unit factor for this
  pool × component monthly_amount) × 12 ≈ annual_amount
  (±$1 rounding).
- For a `parking_space` or `specified_value` component:
  (annual_amount / denominator_value / 12) ≈ printed
  per-recipient amount.

Status semantics same as the aggregate checks: status=pass on
tolerance, status=fail when DRE disagrees with the recomputed
total (preserve DRE value verbatim).

For each check, record a validation_check entry. Status semantics:
read the status field's description for the meaning of pass / fail
/ warning / not_applicable, and pick the value whose definition
matches what you observed. NEVER fix discrepancies by mutating the
extracted values; record the disagreement and move on.

STEP 9: Identify questions for human review
For every issue that requires human judgment, produce a
human_review_question entry with a clear question, the reason it
requires judgment, and the relevant source pages. The severity
field's description explains how to pick between low / medium /
high. Common triggers:
- denominator mismatch (DRE-stated denominator vs recalculated total)
- missing commercial unit value
- unclear pool recipient scope
- unknown allocation method
- unclear whether a budget line is fixed/equal or variable
- unclear rounding reconciliation
- illegible values
- pages that need manual review

ALSO flag any of the following "structural complexity" patterns
that change how next year's assessment math will work. These are
NOT extraction errors — they are operationally important context an
operator must verify yearly:

- Atypical revenue offsets, third-party reimbursements, or
  cost-sharing arrangements with municipalities, water districts,
  school districts, utility districts, or commercial neighbors
  that reduce or shift the HOA's assessable budget.
- Easement, license, or use agreements referenced anywhere in the
  DRE that reduce or shift the HOA's financial obligations.
- Phased buildout structures where the assessment denominator (unit
  count, ownership percentages) is expected to change in future
  years.
- Multiple budget summaries on the same DRE that combine to produce
  the net assessment (e.g. master + sub-association, gross + offset,
  residential + commercial overlay).
- Reserve study assumptions (inflation, interest, tax rate) that
  differ materially from the DRE's stated defaults — when they
  differ, surface the discrepancy.
- Per-pool reserve studies whose inflation or interest assumptions
  differ across pools. Surface the disagreement so the operator
  can confirm it's intentional (e.g. a newer reserve study for
  one pool, older for another) rather than an extraction error.

For each pattern present, produce one human_review_question with
severity=medium asking the operator to confirm the arrangement is
still in effect for the current budget year. Cite the page numbers
where the complexity is documented.
